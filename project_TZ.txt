PROJECT SPECIFICATION — F-Balance

1. КОНЦЕПЦІЯ ПРОЄКТУ

F-Balance — мінімалістичний web-застосунок для персонального контролю харчування.

Основна ідея:
користувач може швидко записати, що він з'їв, отримати орієнтовну калорійність, зберігати власні страви, переглядати статистику харчування та отримувати прості рекомендації щодо наступного прийому їжі.

Проєкт створюється насамперед як pet-project для розвитку frontend-навичок і вивчення нових технологій, тому важливо не просто реалізувати функціонал, а використати сучасний стек і показати роботу з API, AI, авторизацією, базою даних, графіками, локалізацією та адаптивністю.


2. НАВІЩО ПОТРІБЕН ЗАСТОСУНОК

Проблема:
підрахунок калорій часто потребує ручного пошуку продуктів, повторного введення однакових страв та переходу між кількома сервісами.

F-Balance має спростити цей процес:
- швидко додати прийом їжі;
- знайти продукт у готовій базі;
- вручну ввести калорії та КБЖУ;
- створити власну страву один раз і використовувати її повторно;
- визначити орієнтовну калорійність за описом або фотографією;
- бачити поточну статистику за день;
- отримувати рекомендації відповідно до власної цілі.


3. ЦІЛЬ ПРОЄКТУ

Не створити професійний медичний або дієтологічний сервіс, а зробити зручний персональний food-tracking застосунок.

Технічна ціль:
отримати практичний досвід у:
- Vue 3;
- роботі з backend-as-a-service без створення окремого backend-проєкту;
- authentication;
- database;
- file/image storage;
- AI API;
- сторонніх nutrition API;
- data fetching та caching;
- charts;
- form validation;
- i18n;
- responsive/mobile-first UI;
- security rules;
- сезонній темізації.


4. ЦІЛЬОВИЙ КОРИСТУВАЧ

Основний користувач:
людина, яка хоче контролювати харчування та калорійність без складного інтерфейсу.

Перший етап:
застосунок розрахований лише на 2 користувачів, тому немає потреби в дорогій інфраструктурі, масштабуванні чи платних сервісах.

Архітектура при цьому має залишатися нормальною для потенційного подальшого масштабування.


5. ОСНОВНИЙ USER FLOW

1. Користувач відкриває сайт.
2. Бачить короткий landing page з описом можливостей та CTA "Get started / Зареєструватися".
3. Реєструється або входить у систему.
4. Під час першої реєстрації заповнює базову інформацію:
   - ціль;
   - вага;
   - за потреби зріст;
   - рівень фізичної активності;
   - бажані параметри/цілі.
5. На основі даних формується персональна денна ціль.
6. На Dashboard користувач бачить поточний прогрес.
7. Додає їжу:
   - через готовий продукт;
   - через власну страву;
   - вручну;
   - за описом через AI;
   - за фотографією через AI.
8. Протягом дня статистика автоматично оновлюється.
9. На сторінці Recommendations користувач бачить ідеї для наступного прийому їжі.
10. У Profile можна змінити цілі та персональні налаштування.

- редагування;

Страва повинна автоматично перераховувати КБЖУ при зміні кількості інгредієнтів.

- редагувати;
- дублювати;
- видалити;
- додати до поточного прийому їжі.


6.7. AI Calorie Estimator

Окрема функція для оцінки калорійності.

Вхід:
1. фотографія їжі;
2. текстовий опис.

AI повинен повертати тільки:
- орієнтовну кількість калорій.

Для фото бажано також визначати приблизний склад страви, але UI користувачу показує лише calorie estimate, якщо це відповідає вимозі продукту.

Важливе обмеження:
AI не може достовірно визначити точну калорійність за фотографією. Результат має бути позначений як приблизна оцінка, а не як точне значення.

11. DATA STORAGE / BACKEND

Оскільки окремий backend створювати недоцільно, запропоновано використати Supabase.

Supabase закриває:
- Authentication;
- PostgreSQL database;
- Storage для фотографій;
- Row Level Security;
- Edge Functions для server-side логіки.

Це дозволяє мати frontend + backend-сервіси в одному репозиторії/проєкті без написання окремого Node/Nest backend.

Для такого маленького pet-project Free Plan достатній: він включає database, authentication, storage та Edge Functions у межах встановлених лімітів.


12. AI ARCHITECTURE

Не можна безпечно зберігати секретний AI API key безпосередньо у frontend.

Рекомендована схема:

Vue app
   ↓
Supabase Edge Function
   ↓
Gemini API
   ↓
calorie estimate
   ↓
Vue app

Edge Function повинна:
- приймати текст/зображення;
- перевіряти authentication;
- валідовувати input;
- звертатися до AI;
- повертати структурований результат;
- не повертати зайві AI-відповіді.

Для AI можна використати Gemini API. На момент підготовки ТЗ Google має Free Tier для окремих Gemini-моделей, але конкретні моделі та rate limits потрібно перевіряти перед реалізацією.


13. FOOD / NUTRITION API

Для пошуку продуктів запропоновано перевірити Open Food Facts API.

Його можна використовувати для:
- пошуку продуктів;
- отримання калорій;
- білків;
- жирів;
- вуглеводів;
- даних на 100 г/порцію, якщо вони доступні.

Важливо:
API не повинно бути єдиним джерелом. Якщо продукт не знайдений або дані неповні — користувач повинен мати можливість ввести інформацію вручну.


14. RECIPE API

Для рецептів можна використати TheMealDB або інший безкоштовний recipe API.

Рекомендована логіка:
- API використовується як джерело готових рецептів;
- AI може використовуватися для адаптації/генерації рекомендацій;
- не потрібно робити всі рекомендації залежними від AI.

Це зменшує кількість AI-запитів і робить застосунок стабільнішим.

Основний:

Нові технології/бібліотеки:

Не потрібно підключати всі бібліотеки одразу. Частину можна додавати поступово, щоб кожна технологія мала реальну задачу в проєкті.


20. SECURITY

Вимога "сайт не мають зламати" повинна бути сформульована як:
застосунок має мінімізувати типові security-ризики.

Необхідно:
- Supabase Row Level Security;
- користувач має доступ лише до власних даних;
- AI API keys не зберігати у frontend;
- секрети зберігати у server-side environment/secrets;
- валідовувати всі дані;
- обмежити розмір фотографії;
- перевіряти MIME/type файлів;
- не довіряти даним з frontend;
- захистити Edge Functions;
- не зберігати зайві персональні дані;
- обмежити AI requests;
- коректно обробляти помилки;
- не показувати внутрішні помилки backend користувачу.

Також бажано додати базовий rate limit на AI-функції, щоб уникнути безконтрольного використання API.


21. LOADING / ERROR STATES

На кожну асинхронну дію:
- loading state;
- disabled state;
- success state;
- error state.

Особливо:
- login;
- registration;
- add food;
- AI analysis;
- upload photo;
- save meal;
- recommendations;
- profile update.

Не залишати користувача без пояснення, що відбувається.


22. AI / CALORIE SAFETY

Застосунок не є медичним або дієтологічним сервісом.

AI-оцінка калорій за фото є приблизною.

Необхідно:
- показувати, що AI result is an estimate;
- не подавати результат як медично точний;
- дозволити користувачу відредагувати значення перед збереженням;
- не генерувати небезпечні рекомендації щодо харчування;
- уникати надмірно жорстких рекомендацій при низькій калорійності.


23. PERFORMANCE

Оскільки основний пристрій — телефон:
- lazy loading сторінок;
- оптимізація зображень;
- compression перед upload;
- мінімум важких залежностей;
- caching API results;
- debounce для пошуку;
- pagination/limit для великих списків;
- не завантажувати весь history одразу.


24. PHOTO HANDLING

Перед відправкою фотографії:
- перевірити формат;
- перевірити максимальний розмір;
- стиснути зображення;
- за можливості зменшити resolution;
- відправляти лише необхідний файл.

Для цього можна додатково використати image compression library, якщо нативного browser API буде недостатньо.


25. СЕЗОНАЛЬНА ЛОГІКА

Створити єдину структуру:

themes = {
  spring: {...},
  summer: {...},
  autumn: {...},
  winter: {...}
}

При старті застосунку:
1. отримати поточну дату;
2. визначити сезон;
3. вибрати theme;
4. встановити CSS variables.

Ця логіка має бути ізольована від UI.

- сайт коректно працює на телефоні;
- loading/error states реалізовані;
- AI API key не доступний frontend;
- AI-результат можна підтвердити/відредагувати;
- застосунок не залежить від одного зовнішнього API.

33. ВАЖЛИВЕ ТЕХНІЧНЕ РІШЕННЯ

Не варто робити прямий виклик Gemini API з Vue frontend, якщо для цього потрібен секретний API key.

Краще:
Vue → Supabase Edge Function → Gemini.

Так AI key не потрапляє у browser bundle, а Edge Function може перевірити користувача, обмежити кількість запитів та провалідувати дані.

Також не потрібно робити окремий backend-сервер: Supabase виступає backend-as-a-service.


34. ОБМЕЖЕННЯ ПРОЄКТУ

- лише 2 користувачі на першому етапі;
- без платної інфраструктури;
- без складного окремого backend;
- лише українська та English;
- mobile-first;
- мінімалістичний UI;
- AI використовується лише там, де він справді приносить користь;
- калорійність за фото є приблизною;
- не робити медичний/дієтологічний сервіс;
- не перевантажувати MVP функціоналом.
