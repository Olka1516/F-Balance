# Документація: Ліміти та обмеження

## 1. Загальна філософія

Основний принцип: **зовнішні API не повинні бути критичною залежністю** для базового функціоналу сайту.

Це означає, що для кожного зовнішнього сервісу має бути передбачений fallback-сценарій:

| Сервіс          | Якщо недоступний / ліміт вичерпано                                                      |
| --------------- | --------------------------------------------------------------------------------------- |
| Open Food Facts | Користувач вводить калорії/КБЖУ вручну                                                  |
| Claude AI       | AI-аналіз недоступний, manual entry залишається робочим                                 |

Другий принцип: **економність за замовчуванням**, навіть якщо поточних лімітів вистачає із запасом для 2 користувачів. Це закладається в архітектуру одразу, а не «на потім».

## 2. Open Food Facts API

**Офіційні ліміти:**

- 15 запитів/хв/IP — запит конкретного продукту (по barcode/id)
- 10 запитів/хв/IP — пошук (search)
- Заборонено використовувати search-as-you-type без обмежень

**Обов'язкові заходи:**

- Debounce на пошуковому інпуті: **500–800 мс**
- Мінімальна довжина пошукового запиту: **2–3 символи**
- Кешування результатів через TanStack Query (`staleTime`, напр. 10 хв)
- Не робити повторний запит для вже знайденого продукту (кеш по query-key)
- Ліміт/пагінація кількості результатів на один запит
- При досягненні ліміту — показувати користувачу повідомлення («Спробуйте пізніше»), а не продовжувати спроби

## 3. Claude API (AI-оцінка калорій)

Провайдер: Anthropic Claude, модель `claude-haiku-5-5` (фото + текст, платний API за фактичним використанням через Anthropic Console). Змінюється секретом `ANTHROPIC_MODEL`. Код провайдера ізольований у `_shared/nutrition.ts`.

**Ключ:**

- `ANTHROPIC_API_KEY` зберігається **тільки** в секретах Supabase: `npx supabase secrets set ANTHROPIC_API_KEY=...`
- Ніколи в `.env`, ніколи з префіксом `VITE_`, ніколи в репозиторії чи клієнтському бандлі
- Клієнт отримує тільки оцінку або код помилки — без сирих відповідей провайдера

**Ліміти на користувача (SQL-функція `reserve_ai_request` — єдине джерело правди):**

- Cooldown **3 с**, **20 / годину**, **60 / день**
- Невдалі виклики **не рахуються**
- Слот резервується **до** виклику моделі під advisory lock — паралельні запити не обходять ліміт
- Резервація `pending`, старша за 2 хв, не рахується
- Кеш 48 год: той самий опис / те саме фото → готова оцінка без нового виклику і без витрати ліміту
- Писати в `ai_requests` напряму не можна — тільки через функції

**Інші заходи:** явна дія користувача; фото стискається на клієнті й не зберігається; користувач редагує оцінку перед збереженням; без AI працюють пошук і ручне введення.

```
Vue → Edge Function (auth → reserve_ai_request → Claude → complete_ai_request) → Vue
```

## 5. Supabase

**Free plan (орієнтовно, перевіряти актуальні цифри):**

- 500 MB database на проєкт
- 1 GB file storage
- 5 GB bandwidth
- 50 000 MAU

Для 2 користувачів — запас величезний, платний план не потрібен.

**Обов'язкові заходи:**

- RLS (Row Level Security) на всіх user-specific таблицях — користувач не повинен мати доступу до чужих записів
- Обмеження максимального розміру завантажуваних файлів (фото страв)
- Не зберігати фотографії довше, ніж потрібно: якщо фото використовується лише для AI-аналізу — не тримати його в Storage після обробки (або задати короткий retention)
- Ключі Supabase (anon/service) розділяти за призначенням; service-key ніколи не в клієнті

## 6. Глобальний рівень захисту (Application-level rate limiting)

Навіть якщо на фронтенді десь трапиться баг (наприклад, цикл із 100 запитів), має бути друга лінія захисту — на рівні Edge Function / бекенд-логіки.

Загальна логіка перевірки перед будь-яким зовнішнім запитом:

```
Дія користувача
     ↓
Чи можна зробити запит зараз?
 (ліміт / cooldown / cache)
     ↓
 ┌── ТАК → взяти з кешу або зробити запит
 │
 └── НІ  → показати повідомлення "Спробуйте пізніше"
```

## 8. Що обов'язково зафіксувати в ТЗ

- Debounce для будь-якого пошуку по зовнішньому API
- AI викликається лише вручну, ніколи автоматично
- Кешування (TanStack Query `staleTime`) для всіх server-state запитів
- Ключі AI/сторонніх сервісів — тільки на бекенд-стороні (Edge Functions)
- Кожен зовнішній сервіс — з fallback-сценарієм, що не ламає основний функціонал сайту
